Database Indexing

B+ Tree, data pages, disk-block mapping, clustered indexing and non-clustered indexing — with the storage-level picture that interviewers often expect.

1. B+ Tree — the index structure

  • A B+ Tree is a balanced, multi-way search tree commonly used for database indexes.
  • All leaf nodes are at the same level, so lookup depth stays predictable.
  • Internal nodes mainly store separator keys used for routing.
  • Leaf nodes contain the indexed keys and references to the actual data.
  • Leaf nodes are linked, making sequential and range scans efficient.
Example B+ Tree
40 | 80
↓
10 | 20 | 30
40 | 50 | 60
80 | 90 | 100
↓

20, 25, 30

Linked leaves support efficient range traversal after the first matching key is found.

Search key→Traverse B+ Tree→Leaf entry→Data Page→Rows

2. Data Page — where table rows live

A data page is a fixed-size storage unit used by a database to hold table records. The exact size and layout are database-engine-specific.

Typical structure of a data page

Page type

Slot 1 →
Slot 2 →
…
Slot N →

Row 1 data
Row 2 data
…
Row N data

The slot directory lets the engine locate records within the page even when records move because of updates or variable-length rows.

Important distinction: A B+ Tree leaf entry normally gets you to a page/record reference; the data page contains the actual table row. Do not confuse the index page with the table's data page.

3. Data Page → Data Block mapping on disk

The database presents storage through logical pages, while the underlying storage device reads physical blocks/sectors through the filesystem and storage stack. In many database systems, a database page is designed to align with a storage block, but the exact mapping is implementation-dependent.

Logical page to disk storage
B+ Tree leaf
Key 40 → Page ID 101
Key 50 → Page ID 102
Key 60 → Page ID 103
→
Disk / Storage
Block 101 · Page 101
Block 102 · Page 102
Block 103 · Page 103

Conceptually: B+ Tree → page identifier → database reads the corresponding page into the buffer pool → rows are read from that page.

Index lookup→Page ID→Buffer Pool / Memory→Disk I/O if page is not cached→Read row
Interview point: Indexing mainly reduces the number of pages the database must examine. Fewer page reads generally means less I/O and faster queries.

4. Clustered Indexing

  • The table's data is physically organized in the order of the clustered index key (more precisely, the leaf/data pages follow that key order).
  • Because the data itself is organized around that key, range scans can be very efficient.
  • A table can generally have only one clustered index because the physical row/page ordering can have only one primary organization at a time.
  • In a clustered B+ Tree, the leaf level represents the table data itself or references data pages organized in that order, depending on the database implementation.
Clustered example — key order follows the data pages
B+ Tree leaf: 10 | 20 | 30→Page 1: 10, 15, 18→Page 2: 20, 25, 30→Page 3: 40, 45, 50

The important idea is physical locality/order by the indexed key, not that every database implements the leaf level identically.

5. Non-Clustered Indexing

  • The index is stored separately from the actual table data.
  • A table can have multiple non-clustered indexes.
  • Leaf entries contain the indexed key plus a row locator — for example a Row ID, primary key, or another database-specific pointer.
  • The database may need an additional lookup from the index entry to the data page/row. This is often called a key lookup or bookmark lookup.
Non-clustered example — extra lookup
B+ Tree leaf: key 40 → Row ID 104→Data Page 12→Row 104

The index gets you to the row locator; the separate data structure contains the actual row.

7. Interview mental model

Index = GPS → tells the database where to look.
B+ Tree = navigation structure → quickly narrows the key range.
Data Page = container of rows → actual records live here.
Page → disk block → storage mapping determines where the page is read from when it is not already in memory.
Clustered index → the table data is organized around that key.
Non-clustered index → separate index + row locator + possible extra lookup.
