SECURITY · AUTHORIZATION

OAuth 2.0

How an application gets limited access to protected resources without asking the user to share their password with the application.

01

What is OAuth 2.0?

An authorization framework, not an authentication protocol.

OAuth 2.0 lets a resource owner grant an application limited access to resources hosted by another service, without sharing the resource owner's credentials with that application.

Interview distinction: OAuth answers “what can this app access?” Authentication answers “who is this user?”. OpenID Connect (OIDC) adds an identity layer on top of OAuth 2.0.
02

Roles / Actors involved

Four core OAuth roles.

1. Resource Owner

Usually the user who owns the protected data.

2. Client

The application requesting access to the resource owner's data.

3. Authorization Server

Authenticates the user, obtains consent, and issues authorization credentials such as an access token.

4. Resource Server

Hosts the protected resources and accepts valid access tokens.

04

OAuth 2.0 API Request Flow

Authorization Code flow with PKCE.

User
→
Client
→
Authorization Server

1. Client generates a code_verifier and derived code_challenge.

2. Client redirects the user to:

GET /oauth/authorize
  ?client_id=CLIENT_ID
  &redirect_uri=https://app.example.com/callback
  &response_type=code
  &scope=read:profile
  &code_challenge=CHALLENGE
  &code_challenge_method=S256

3. Authorization server authenticates the user and asks for consent.

4. Authorization server redirects the browser back:

GET https://app.example.com/callback?code=AUTH_CODE

5. Client sends the code to the token endpoint:

POST /oauth/token
Content-Type: application/x-www-form-urlencoded

grant_type=authorization_code
&code=AUTH_CODE
&redirect_uri=https://app.example.com/callback
&client_id=CLIENT_ID
&code_verifier=ORIGINAL_VERIFIER

6. Authorization server validates the code, client, redirect URI and PKCE verifier, then returns tokens.

{
  "access_token": "ACCESS_TOKEN",
  "token_type": "Bearer",
  "expires_in": 3600,
  "refresh_token": "REFRESH_TOKEN"
}

7. Client calls the protected resource:

GET /api/profile
Authorization: Bearer ACCESS_TOKEN

8. Resource server validates the access token and returns the protected resource.

05

Example — “Sign in with Google”

In practice, “Sign in with Google” is typically OAuth 2.0 + OpenID Connect.

User
→
Your App
→
Google Authorization Server
  1. User clicks Sign in with Google on your app.
  2. Your app redirects the browser to Google's authorization endpoint with client_id, redirect_uri, scope, response_type=code, and PKCE parameters.
  3. User logs in to Google and approves the requested scopes.
  4. Google redirects back to your callback URL with an authorization code.
  5. Your backend exchanges the code at Google's token endpoint and receives tokens.
  6. For OIDC, the client can receive an ID token containing identity claims such as the user's subject identifier and email (subject to scopes/claims).
  7. The app uses the access token to call permitted Google APIs, such as a profile/resource API, if those scopes were granted.
Important: an ID token is for the client to learn/authenticate the user's identity in OIDC; an access token is for calling protected APIs. Do not treat an ID token as a general API access token.
06

Key tokens & terms

The vocabulary interviewers commonly test.

Authorization Code

Short-lived, one-time credential returned through the redirect. Exchanged for tokens.

Access Token

Credential presented to a resource server to access protected resources. Usually short-lived.

Refresh Token

Used at the authorization server to obtain a new access token without asking the user to authenticate again.

Scope

Defines what access is being requested, such as profile, email, or api.read.

PKCE

Proof Key for Code Exchange. Protects the authorization-code exchange against interception, especially for public clients.

Redirect URI

Pre-registered callback location where the authorization server sends the authorization response.

07

Interview summary

Remember the flow, not just the names.

User → grants permission → Authorization Server → issues code/token → Client → presents access token → Resource Server → returns protected data.

Best default for user authorization: Authorization Code + PKCE.

Machine-to-machine: Client Credentials.

Authentication / “Who is the user?”: OAuth alone is not enough; use OIDC when identity is required.
