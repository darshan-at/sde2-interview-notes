DATABASES · CONCURRENCY

Distributed Concurrency Control

How multiple requests, threads, processes and servers safely update shared data without losing correctness.

01

Why do we need concurrency?

Many users should be able to work at the same time without corrupting shared state.

Suppose two users read an account balance of ₹1000 at the same time. Both withdraw ₹700. If both independently write back ₹300, the system has lost one update. Without concurrency control, interleaving operations can violate business rules.

User A
→
Read ₹1000
→
Write ₹300

User B
→
Read ₹1000
→
Write ₹300
Goal: allow concurrency for performance, while making the result equivalent to a safe/valid execution according to the chosen isolation guarantees.
02

What is a Transaction?

A logical unit of database work.

ACID

  • Atomicity: all operations commit, or none do.
  • Consistency: constraints/invariants remain valid after commit.
  • Isolation: concurrent transactions do not observe prohibited intermediate effects.
  • Durability: committed data survives failures.

Example: money transfer

  1. Debit ₹500 from A.
  2. Credit ₹500 to B.
  3. Commit only when both succeed.

If the credit fails, the debit must not remain committed.

03

What is DB Locking?

A mechanism to control who can read/write a piece of data concurrently.

Shared (S) Lock

Used for reading. Multiple transactions can usually hold shared locks together, but a conflicting exclusive lock is blocked.

Exclusive (X) Lock

Used for writing. Other conflicting reads/writes are blocked until the lock is released.

Typical flow

Transaction
→
Acquire lock
→
Read / Write
→
Commit / Rollback
→
Release

Important: locking can create waiting and deadlocks, so databases use lock ordering, timeouts/deadlock detection, and different locking granularity.

Isolation Levels

Higher isolation generally prevents more anomalies, but can reduce concurrency or increase coordination.

Dirty Read

T2 reads data written by T1 before T1 commits. T1 may later roll back.

Non-Repeatable Read

T1 reads a row twice and sees different committed values because T2 updated it between reads.

Phantom Read

T1 repeats a range query and sees new/deleted matching rows because T2 changed the range.

Interview note: exact behavior of Repeatable Read, locking and MVCC differs by database engine. Always name the database when discussing implementation details.
05

Ways to achieve concurrency control

Two broad approaches: synchronize access, or detect/coordinate conflicts.

1) Synchronize

Serialize conflicting access using mutexes, monitors, semaphores, locks or distributed locks.

  • Simple mental model.
  • Useful when a shared critical section must have one owner.
  • Can reduce parallelism and introduce contention.
  • Distributed locks need careful ownership, expiry and failure handling.

2) Distributed Concurrency Control

Coordinate concurrent operations across multiple processes/nodes while preserving database correctness.

  • Pessimistic: assume conflicts are likely; block using locks.
  • Optimistic: assume conflicts are rare; validate/version-check and retry on conflict.
06

Pessimistic vs Optimistic

The classic interview comparison.

Pessimistic Concurrency Control

Read
→
Lock
→
Modify
→
Commit
  • Assumes a conflict is likely.
  • Locks data before a conflicting operation.
  • Other transactions may wait.
  • Good when contention is high and retries are expensive.
  • Risks: deadlocks, blocking and lock contention.

Optimistic Concurrency Control

Read + version
→
Modify
→
Validate
→
Commit / Retry
  • Assumes conflicts are rare.
  • Usually avoids holding locks during the whole business operation.
  • At commit, checks whether the data/version changed.
  • If validation fails, abort/retry with fresh data.
  • Good for low-contention workloads and long-running reads.

08

Extra interview points

These are often where follow-up questions go.

MVCC

Multi-Version Concurrency Control keeps multiple versions of rows so readers can often proceed without blocking writers. Different databases implement snapshots and visibility rules differently.

Deadlock

T1 holds A and waits for B, while T2 holds B and waits for A. Databases can detect cycles and abort one transaction, or use timeouts.

Lost Update

Two writers read the same old value and overwrite each other's work. Locks or version checks can prevent it.

Distributed transaction

When one logical transaction touches multiple nodes/services, coordination becomes harder. Protocols such as two-phase commit can provide atomic commit, while consensus-based systems may provide replication/coordination primitives.
