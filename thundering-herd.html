DISTRIBUTED SYSTEMS · PERFORMANCE

Thundering Herd Problem

When a large number of clients, threads, or processes wake up or retry together and hit the same resource, creating a sudden load spike.

01

What is the Thundering Herd?

Many waiting actors become active at the same time.

The Thundering Herd Problem happens when many clients/threads/processes are waiting for a shared resource and then all wake up, retry, or request it simultaneously.

Simple analogy: a stadium gate opens and thousands of people rush through at once. The gate is available, but the sudden burst creates a queue and slows everything down.

It is common around cache expiration, locks, scheduled jobs, service recovery, connection pools, and event notifications.

02

How does it happen?

The pattern is usually the same.

Many clients waiting
→
Resource becomes available
→
All wake / retry
→
Sudden load spike
  1. Many clients are waiting for a cache key, lock, connection, event, or scheduled time.
  2. The resource becomes available.
  3. Many or all waiting clients wake up or retry together.
  4. They hit the backend/resource at nearly the same time.
  5. The resource becomes overloaded, causing latency, failures, and even more retries.
03

Classic Example: Cache Stampede

A very common form of thundering herd.

Client 1
↘
Cache miss / expired
→
Database
→
Sudden spike

Suppose 10,000 requests need the same hot key product:123. The key expires at roughly the same time. Instead of one request rebuilding the value, many requests observe the miss and hit the database together.

10,000 requests
      ↓
Cache key expired
      ↓
10,000 cache misses
      ↓
10,000 DB requests  ← dangerous
      ↓
DB overload / timeouts
Important: the cache did its job normally. The problem is that too many requests reacted to the same cache miss at once.
04

Why is it dangerous?

The failure can become self-amplifying.

Resource overload

CPU, memory, database connections, thread pools, or downstream services can be exhausted.

Latency & timeouts

The sudden queue increases response time and causes requests to time out.

Cascading failures

An overloaded dependency can make upstream services fail too.

Retry amplification

Timeouts trigger retries, which create even more load — turning one spike into a feedback loop.

05

Common Scenarios

Look for synchronized wake-ups.

Where can the herd appear?
ScenarioWhat synchronizes?Result
Cache expirationMany requests see the same key expireMany backend/database fetches
Lock releaseMany threads wait for one lockMany wake and contend for the lock
Scheduled jobsMany jobs are scheduled at the same timeCPU/network/database spike
Service recoveryClients retry after an outageRecovered service is hit by everyone at once
Event notificationMany consumers wake on one eventConsumer/downstream burst
06

How to Mitigate It?

Break synchronization and avoid duplicate work.

1. Request Coalescing / Single-Flight

Allow only one request to fetch or rebuild the missing data. Other requests wait for the same result and reuse it.

2. Distributed Lock

Use a lock so only one worker rebuilds/fetches the resource while others wait or serve a fallback.

3. Randomized TTL / Jitter

Add randomness to expiration times so many keys do not expire simultaneously.

4. Exponential Backoff + Jitter

Retry with increasing delays plus randomness. Jitter prevents clients from retrying in synchronized waves.

5. Stale-While-Revalidate

Serve slightly stale data while one request refreshes the value in the background.

6. Rate Limiting / Load Shedding

Put a ceiling on incoming work so a recovered or overloaded backend is not flooded.

08

Interview Takeaway

The 30-second answer.

The Thundering Herd Problem occurs when many clients, threads, or processes become active at the same time and hit a shared resource, causing a sudden load spike.

A classic example is cache expiration: thousands of requests see a cache miss and all hit the database together.

Mitigate it by breaking synchronization and avoiding duplicate work — use request coalescing/single-flight, distributed locks, TTL jitter, exponential backoff with jitter, stale-while-revalidate, and rate limiting.
