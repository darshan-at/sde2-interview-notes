Cache Strategies

Use a cache to reduce latency, backend load and bandwidth.

What is a cache?

A temporary storage layer that keeps frequently accessed data so future requests can be served faster.

  • Reduces response time by serving data from memory.
  • Reduces load on DB and backend services.
  • Improves scalability and can reduce cost.

Key terms

Cache Hit
Requested data is found in the cache.
Cache Miss
Data is not in the cache and must be fetched.
TTL
How long an item remains in the cache.
Eviction
Removing data when the cache is full.
Consistency
Keeping cache data aligned with the DB.
Client
→
Cache
Redis / Memcached
→

Hit → return quickly · Miss → read DB → populate cache → return

Cache-Aside (Lazy Loading)

  1. Application checks cache.
  2. On miss, reads from DB and stores the result in cache.
  3. On write, updates DB and invalidates cache.

Good default for many read-heavy systems.

Write-Through

  1. Write goes to cache.
  2. Cache synchronously writes to DB.

Strong consistency; higher write latency.

If DB update fails, the application must also roll back the cache update.

Write-Back (Write-Behind)

  1. Write to cache first.
  2. DB is updated asynchronously later.

High write performance and fewer DB writes.

Cache/server failure can risk data loss; more operational complexity.

Read-Through

  1. Application talks to cache.
  2. On miss, cache fetches from DB and returns the data.

Simplifies client logic; cache owns loading.

Refresh-Ahead

  1. Cache predicts that a hot item is about to expire.
  2. It refreshes the item before expiry.

Useful for predictable, frequently accessed data.

SQL vs NoSQL

The distinction is primarily about the data model and database paradigm, not centralized vs distributed deployment.

Important: Both SQL and NoSQL databases can be deployed in centralized or distributed environments.

How modern SQL can be distributed

Systems such as Google Spanner, CockroachDB, YugabyteDB and TiDB can distribute relational data across nodes while preserving a SQL interface and strong transactional guarantees.

  1. Partitioning / sharding: split data across nodes.
  2. Replication: keep copies on multiple nodes.
  3. Distributed query processing: route work to relevant nodes and combine results.
  4. Distributed transactions: coordinate multi-node operations using protocols such as 2PC or consensus mechanisms.

Use SQL when

  • Data is structured and relational.
  • Complex queries and joins are required.
  • ACID transactions and consistency are critical.
  • Examples: banking, ERP, inventory, reporting.

Use NoSQL when

  • Data is unstructured or semi-structured.
  • High scalability and availability are priorities.
  • Large volumes of distributed data are expected.
  • Examples: social media, IoT, real-time analytics, caching.

Database Indexing

B+ Trees, data pages, clustered and non-clustered indexes — the interview version.

Why indexing?

  • Without an index, the DB may scan every row: full table scan.
  • An index helps the DB quickly locate the required rows.
  • Typical trade-off: faster reads, but extra storage and write/update work.

B+ Tree

  • A balanced multi-way tree commonly used for database indexes.
  • All leaf nodes are at the same level.
  • Internal nodes mainly store keys used for routing.
  • Leaf nodes store indexed entries and are linked for sequential/range access.

Clustered Index

  • The table rows are stored in the same order as the indexed key.
  • There can generally be only one clustered ordering per table.
  • Often excellent for range queries and ORDER BY on the clustered key.
  • Leaf level can contain the actual row data (implementation varies by DB).

Non-Clustered Index

  • The index is stored separately from the actual table data.
  • Multiple non-clustered indexes can exist on a table.
  • Leaf entries contain the indexed key plus a locator such as Row ID or clustered key.
  • Lookup may require an extra step to fetch the actual row: a bookmark/key lookup.

Active-Passive vs Active-Active Clustering

A cluster is a group of servers working together to provide a service.

Active-Passive

  • One server/group is active and handles traffic.
  • Another is passive (standby) and normally serves no production traffic.
  • If active fails, passive is promoted.
Load Balancer→Active AorPassive B

How does passive know?

A health monitor checks heartbeats or health endpoints. If heartbeats stop, the system detects failure and promotes B.

Active-Active

  • Both servers are active and serve traffic.
  • Load balancer distributes requests.
  • If one fails, traffic is redistributed to the other — no promotion step.
Load Balancer→Server A+Server B

Big challenge: state consistency

If both servers independently maintain mutable state, concurrent writes can produce inconsistent views.

Example: A and B both start with balance ₹1000. A processes a ₹200 withdrawal and thinks ₹800 remains, while B still thinks ₹1000 remains. Shared state or a carefully designed consistency mechanism is required.

Advantages / disadvantages

Active-PassiveActive-Active
Simpler consistency; single writerHigher resource utilization
Easier failure managementBetter availability without promotion
Standby capacity is underutilizedState and multi-writer conflicts are harder
Failover downtime is possibleRequires careful idempotency, locking, versioning, etc.

State management

Prefer application servers to be stateless. Store shared state in systems such as a database, Redis, or another external durable store.

Split brain: During a network partition, both nodes may believe the other is down and become active. If both accept writes, data corruption or inconsistency can occur. Use quorum, fencing, leader election or another mechanism appropriate to the system.

Proxy, Reverse Proxy, Load Balancer, VPN & Firewall

Five networking building blocks that are easy to mix up in interviews.

1. Proxy (Forward Proxy)

Sits between the client and destination server and acts on behalf of the client.

  • Hides client identity from the destination.
  • Security, monitoring, caching and access control.
  • Can block unwanted websites.
Client→Proxy→Internet

2. Reverse Proxy

Sits in front of backend servers and acts on their behalf.

  • Hides backend servers from clients.
  • Can terminate SSL/TLS.
  • Routes by URL, host, headers, etc.
  • Can provide caching, compression and authentication.
Client→Reverse Proxy→Servers

3. Load Balancer

Distributes incoming traffic across multiple healthy backend servers.

  • Improves availability and scalability.
  • Prevents one server from becoming overloaded.
  • Performs health checks.
  • Algorithms include Round Robin, Least Connections, IP Hash and Weighted Round Robin.

4. Firewall

Controls incoming and outgoing network traffic using security rules.

  • Barrier between trusted and untrusted networks.
  • Can filter by IP, port and protocol.
  • Types include network firewall, host-based firewall, stateful firewall and NGFW.

5. VPN

Creates a secure, encrypted tunnel over an untrusted network such as the Internet.

  • Connects users or sites to private networks.
  • Provides confidentiality, integrity and authentication.
  • Common protocols: IPsec, OpenVPN, WireGuard.
User→Encrypted tunnel→Private network
