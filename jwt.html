SECURITY · TOKENS

JSON Web Token (JWT)

A compact, signed token format commonly used to carry claims between parties and to authenticate API requests.

01

What is JWT?

A token format — not a complete authentication system.

JWT (JSON Web Token) is a compact, URL-safe representation of claims that can be digitally signed and, in some variants, encrypted.

Key idea: the server can verify that a signed JWT was issued by a trusted party and that its contents were not modified. Signing does not hide the payload; normal JWT payloads are Base64URL-encoded, not encrypted.
02

JWT Structure

Three Base64URL-encoded parts separated by dots.

HEADER.PAYLOAD.SIGNATURE

eyJhbGciOiJSUzI1NiIsInR5cCI6IkpXVCJ9
.
eyJzdWIiOiIxMjMiLCJleHAiOjE3... 
.
<digital-signature>

1. Header

Metadata about the token.

{
  "alg": "RS256",
  "typ": "JWT",
  "kid": "key-123"
}

alg = signing algorithm. kid can identify the verification key.

2. Payload

Claims about the subject and token.

{
  "sub": "123",
  "iss": "auth.example",
  "aud": "orders-api",
  "exp": 1790000000
}

Common claims: iss, sub, aud, exp, iat.

3. Signature

Lets the verifier detect tampering and verify the issuer, assuming the signing key is trusted.

Sign(
  base64url(header)
  + "." +
  base64url(payload),
  signing_key
)
03

JWT Request Flow

Typical stateless API authentication.

User
→
Login
→
Auth Server
→
Signed JWT
→
Client

1. User authenticates with the authorization/authentication service.

2. Server issues a signed access token (JWT).

3. Client sends it with each API request:

GET /api/orders
Authorization: Bearer <JWT>

4. API validates signature and relevant claims such as iss, aud, and exp.

5. If valid, the API authorizes the requested operation and returns the response.

04

JWT vs Session ID

Both can authenticate a user, but state is handled differently.

Stateless token vs server-side session
AspectJWTSession ID
What client storesToken containing claimsOpaque session ID
Server-side stateCan be stateless for access-token validationUsually stores session data in memory/DB/cache
ValidationVerify signature + claimsLook up session ID and session state
RevocationHarder before token expiry unless you add state/deny lists or use short TTLsEasy: delete/invalidate the session
Horizontal scalingConvenient because validation can be local; keys must be availableNeeds shared session store or sticky sessions
PayloadClaims travel with the requestData stays server-side
Token sizeUsually largerUsually small
Interview takeaway: JWT is not automatically “better” than sessions. If you need easy server-side revocation and browser session management, a traditional session can be simpler. JWTs are useful when distributed services need independently verifiable tokens.
05

Advantages

Why teams choose signed JWT access tokens.

Stateless validation

The resource server can validate a signed token without a database lookup for every request.

Good for distributed systems

Multiple API instances/services can validate the same token using a trusted public key.

Self-contained claims

Useful claims such as subject, issuer, audience and expiry travel with the token.

Standard format

JWT is widely supported across languages and platforms and fits naturally with HTTP Bearer authentication.

06

Challenges / Pitfalls

The part interviewers often care about.

Revocation is harder

A valid JWT normally remains valid until its expiry. Short-lived access tokens plus refresh-token mechanisms are common mitigations.

Stolen token = usable credential

Bearer tokens should be protected like passwords. Use TLS, safe storage, short lifetimes and appropriate cookie protections.

Payload is not secret

Never put passwords, secrets or sensitive data in an ordinary signed JWT just because it is Base64URL encoded.

Key rotation

Signing keys must be rotated safely. Consumers need a way to discover current verification keys.

Large tokens

Too many claims increase request/header size and network overhead.

Validation mistakes

Do not blindly trust claims. Validate the expected algorithm, issuer, audience, expiry and signature according to your security design.

07

Where should JWT be used?

Use it when its properties solve a real problem.

Good fits

  • Short-lived API access tokens in distributed systems.
  • Microservices/resource servers that need locally verifiable credentials.
  • Federated/OAuth 2.0 and OpenID Connect ecosystems where JWTs are part of the token or identity format.
  • Systems where carrying a small, well-defined set of claims is useful.

Think twice

  • Simple server-rendered web apps where a session cookie is easier.
  • Systems requiring immediate, simple revocation of every login.
  • Cases where teams are tempted to put lots of application data into the token.
Rule: choose JWT for its verification/distribution properties — not simply because “stateless is better.”
08

JWK — JSON Web Key

How systems publish the public keys used to verify JWT signatures.

JWK is a JSON representation of a cryptographic key. A JWKS (JSON Web Key Set) is a JSON object containing a set of JWKs.

{
  "keys": [
    {
      "kty": "RSA",
      "kid": "key-123",
      "use": "sig",
      "alg": "RS256",
      "n": "...",
      "e": "AQAB"
    }
  ]
}

kid=key-123
→

→
Find matching public key
→
Verify JWT signature
Why JWK/JWKS matters: with asymmetric signing such as RS256, the issuer keeps the private key secret while resource servers can obtain the corresponding public key. Key rotation becomes manageable because new keys can be published alongside old keys during the transition.
09

JWT + OAuth 2.0

Do not confuse the token format with the authorization framework.

OAuth 2.0
How access is granted
+
JWT
One possible token format
→
Protected API

OAuth 2.0 defines how a client obtains delegated access. The resulting access token may be a JWT, but OAuth 2.0 does not require JWT access tokens.

Similarly, OIDC uses JWT-based ID tokens for identity claims. An ID token should not automatically be treated as an API access token.

10

Interview Summary

The 30-second answer.

JWT is a compact, signed token format containing claims. Its three parts are Header + Payload + Signature. A server verifies the signature and claims to authenticate/authorize a request.

Compared with Session ID: JWTs can enable stateless validation across distributed services, but revocation and token lifecycle management are harder.

Use: especially for short-lived API access tokens in distributed/federated systems — not as a default replacement for every session.

JWK/JWKS: standard JSON representations of cryptographic keys/key sets, commonly used to publish public verification keys and support JWT key rotation.
